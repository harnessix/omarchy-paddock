# Changelog

## Unreleased

- New: `paddock freeze <id>` and `paddock thaw <id>` (`--tree` for the sandboxes it started, `--reason` for the record). A frozen sandbox uses no CPU and keeps its memory; thawed, it continues where it stopped. With a systemd user instance, every bwrap or srt sandbox now starts in a scope of its own (`paddock-sb-<id>`): a small start stub stops, paddock moves it into a new transient scope over D-Bus, and the stub becomes the sandbox command, so the environment does not change. Freezing uses the cgroup freezer of that scope, over D-Bus, and only of a `paddock-` scope; docker and podman sandboxes are paused. `paddock ps` and the bar panel show how long a sandbox has been frozen, and the panel has a key to freeze and thaw. `paddock stop` thaws first. Each freeze and thaw is in the audit log, and paddock kv holds `sandbox:<id>` with the state for the other agents of the project.
- Fix: the approval hook starts again when its script is still busy for a moment ("Text file busy"), instead of failing the request. A kv prefix watch takes the write lock only when a key really expired.
- Fix: a build of paddock no longer takes over your integrations. Before, a build that ran with your own folders (a development run, or a test that did not set temporary folders) could start the background refresh, which wrote the path of the build into your launcher entries, shell commands and the Omarchy menu; once the build was gone, they failed with "Requested executable not found". Now every write of launcher entries, app entries, link handlers, shell commands, the Omarchy menu, the mise wrapper, the Hyprland hook and the systemd units refuses, with the reason, when the running paddock is not the one on `PATH` or lies in a `target/` folder, unless the run uses a home folder other than your real one (as tests do). The background refresh skips such a run. Every test that runs the paddock binary now sets temporary folders, and a test checks that.
- Security: `forge` (gh), `screenshot`, `clipboard-read`, `clipboard-write`, `open-url` and `notify` run in the gateway executor from a signed plan. gh runs the program that paddock found, with the body on standard input, in an empty folder, with the home folder read-only and only its own login and proxy variables. The desktop tools run with no home and no network, and see only the Wayland socket and the compositor's sockets; a copied text stays on the clipboard in a unit of its own. Links open through the desktop portal (OpenURI), so the browser starts outside paddock; without a portal, `xdg-open` gets only the variables that a browser needs. `fetch` and `spawn` stay in the paddock process.
- Security: an approved `git push` runs in the gateway executor, isolated. The plan of the card (scratch repository, URL, refs, the object store it checks) is part of the signed grant, so the executor pushes exactly what was approved. The home folder is read-only there (git and SSH configuration, keys and credential helpers keep working), only the scratch repository and a remote on this machine are writable, and only the variables that git and SSH need pass. Before, the push ran in the paddock process with the whole environment and a writable home.
- Security: an approved `exec` runs isolated. The executor starts it in a transient systemd user unit (or with bwrap without a systemd user instance): the system read-only, the project read-write, an empty home folder, its own `/tmp`, no new privileges, and under systemd no new namespaces. Of the host environment only `PATH`, the language and time zone variables, `TERM`, `USER` and `LOGNAME` pass. Before, the command saw the whole home folder and got every variable of the paddock process, tokens included. `[exec]` in the user configuration widens this (`home = "read-only"|"full"`, `network = false`, `paths`, `ro_paths`, `env`); a project `paddock.toml` with `[exec]` is invalid.
- New: the gateway executor. An approved `exec` no longer runs in the paddock process that runs the sandbox. paddock signs a grant for exactly that request (HMAC-SHA256 over the request hash, the sandbox, the project, a 30-second lifetime and a random number; the key is `$XDG_RUNTIME_DIR/paddock/gateway.key`, mode 0600, new at each login), and a separate process, `paddock gatewayd`, runs it only when the signature, the time, the request and a never-used number match. paddock starts the executor when a request needs it, and it stops after two minutes without requests. `paddock gateway install` hands the start to systemd (socket activation), `paddock gateway remove` takes it back, and `paddock doctor` shows which one is in use. The other capabilities follow.
- Security: `fetch` refuses paddock's own folders (data, state, configuration, cache): sandbox homes of other projects, approvals, the audit log, paddock kv and the gateway key. Before, an approved fetch could copy them into a sandbox.
- New: the gateway device `/dev/paddock/gw`. Host requests from `paddock-host` go through it instead of the host socket, wherever the sandbox has `/dev/paddock`. paddock names each request by a hash of its normalized capability and arguments (not the reason), so the same request sent again while it waits joins it: one card, one run. A read waits at most 100 seconds (`timeout` 1 to 600); then it fails with `ETIME` (still waiting), and `paddock-host` sends the same request again on its own. A result goes to one reader, once, and a sandbox can have 8 requests waiting. The socket stays for sandboxes without `/dev/paddock`. The gateway and the socket share one broker: the same policy, session grants, cards and audit log.
- Fix: a SIGTERM or a SIGHUP no longer ends paddock before its exit steps. Before, a closed terminal, a `kill`, or the parent of a spawned child that ended, killed the paddock process at once: the `/dev/paddock` mount stayed behind, and a refreshed login, new history and the session record were not saved. Now paddock passes SIGTERM to the sandbox, as `paddock stop` does, waits for it, and runs the exit steps. A stop that comes before the sandbox starts means it does not start. After a SIGHUP, paddock writes nothing to the closed terminal.
- README: the install commands name the latest release tag instead of `main`: `git clone --branch vX.Y.Z`, and download links for the release binary and its checksum. `omarchy plugin add` takes no tag, so the widget still comes from the default branch. When a package owns the binary, `paddock update` names the tag to check out. A test fails when the README, the skill or a package file names another version than `Cargo.toml`.
- The menu entries, the Omarchy menu block and the shell shims stay current. Before, they listed only the harnesses that existed when you turned them on, so an agent installed later, or a profile from a newer paddock (Grok Build, Hermes, Kimi, pi and others), had no entry and no shim. New: `paddock refresh` adds the entries and shims of new harnesses and removes those of harnesses that are gone. A harness start runs it in the background when the paddock version or a folder on `PATH` changed; that run only adds, so a smaller `PATH` can never remove a working shim. `paddock update` runs it with the new version. Only the parts that you turned on change, and `~/.bashrc` and `~/.zshrc` do not. `paddock doctor` names the harnesses that the menu or the shims miss.
- The limits in the Omarchy agents panel are checked from one side at a time. With `paddock shims install --scope omarchy-agent`, paddock adds one marked block at the end of `~/.config/hypr/hyprland.lua`, which puts one folder ahead of Omarchy's `bin` folder on the `PATH` of the programs that Hyprland starts, with one command, `omarchy-agent-usage-update`. `luac -p`, if installed, checks the file before paddock writes it. When no sandbox holds a login, Omarchy's command runs unchanged. While a sandbox holds the login of Claude Code or Grok Build, the host skips that agent, and paddock runs Omarchy's own collector in a sandbox with network mode egress, a read-only home, and the sandbox's copy of the login in place of the host file. A held Codex login is not checked, because its collector can refresh the login: the record keeps its last numbers, marked as paused. paddock checks only when the panel asks. `paddock shims remove` removes the block byte for byte, and `paddock doctor` shows the state. It takes effect at the next login.
- Codex and Grok Build history from `omarchy-agent` starts is copied to the host every five minutes while the sandbox runs, not only at exit, so the Omarchy agents panel counts new sessions sooner. Logins still go back only at exit. `paddock doctor` lists the isolated logins (`--auth isolated:NAME`), which the agents panel does not show.
- Blocking reads replace `sleep`. A read that waits for an event now ends with one status when its `--timeout` passes first: "still waiting", exit code 75 of `paddock-host` (`EX_TEMPFAIL`) and the JSON status `waiting`. This holds for `paddock-host kv watch` and `paddock-host wait` (they exited with 5 before; 5 now means only that nobody answered an approval in time), and for waiting devices, whose plain reads fail with `ETIME`. The agent runs the same read again. The `paddock-host` skill tells agents to loop on such a read with a timeout below the limit of their shell tool, and never to `sleep`.
- New device `/dev/paddock/wait`: the read returns at a time, an RFC 3339 time or a duration, at most seven days ahead. Off until `[devices] wait = true`.
- New device `/dev/paddock/ask`: the agent writes a question, with optional choices, and the read returns your answer. The question shows on the approval card in the bar, with a text field that takes the keyboard only after a click, as a desktop notification without the bar, and in `paddock approvals`. Answer with `paddock approvals answer ID --text TEXT`; `deny` dismisses it, and the agent gets `EACCES`. A read that times out leaves the card open, and the same question again finds it. The audit log records sizes, never the question or the answer. Off until `[devices] ask = true`.
- The `ask` device and host requests are safer to show and to answer. `paddock approvals answer ID --text -` reads the answer from standard input, and the bar panel sends it that way, so an answer never shows in the process list or the shell history; an answer may start with `-`. Text from a sandbox (a question, its choices, the reason of a host request) loses control characters other than newline and tab, and invisible format and bidi characters, before it reaches the card, a notification or `paddock approvals`; a notification server that reads markup gets `&`, `<` and `>` escaped. At most 8 questions of all sandboxes wait at once, a sandbox whose question you dismissed cannot ask again for 30 seconds, and host requests come before questions on the card. Abandoned questions leave the card within ten seconds, also when the agent never asks again, and a question of a sandbox whose paddock was killed leaves it after a minute. Every read of one question gets the answer. A time with a non-ASCII character is refused instead of stopping a host thread.
- Fix: a prefix watch in paddock kv no longer misses a key that expired between two watches. An expiry is now a change in the history, with the op `expire`, so the cursor covers it.
- New: `paddock-host device NAME [REQUEST]`, `device wait TIME` and `device ask QUESTION --choice TEXT` send one device request and turn the errno of a failed read into the exit codes of `paddock-host`. `device list` prints the catalog.
- A prefix watch in paddock kv also wakes when a key under the prefix expires, so `watch --prefix lease:` returns when a lease runs out. The change has the op `expire`.
- Fix: `[devices]` and `[kv]` in `~/.config/paddock/config.toml` made every start fail with "unknown field". The user configuration now accepts them; a project `paddock.toml` with them is still invalid.

- `paddock doctor` tests that agents started from the Omarchy shell (the agents panel, prompts and crash reports run `bash -lc`) reach paddock: a login shell started with Omarchy's bin folder first on PATH must run `omarchy-agent` through mise. Before, doctor only said to check the key by hand.
- paddock kv: a key-value store for agents, on the host. Each sandbox reaches it through its own socket, `paddock-host kv` inside the sandbox. The socket is the identity: a request never names a sandbox, and one that tries is rejected. Scopes: `self` (this run), `project` (every sandbox of the project; each entry records its writer and reads as untrusted), `parent` (read-only, the `self` scope of the sandbox that started this one) and `user` (all projects; asks at the first use through the approval card). Operations: get, mget, put, mset, delete, list by prefix, history, compare-and-swap versions, a time to live for each key, watches on a key or a prefix, and leases with `claim` and `release`, whose owner paddock sets. Limits per value and per scope in `[kv]` of the user configuration. `paddock gc` removes the `self` data of runs that ended more than 30 days ago. The audit log keeps key names and sizes, never values. On the host, `paddock kv list|get|delete|release` reads the store and frees leases.
- Devices: each sandbox gets a FUSE file system at `/dev/paddock`, served by paddock on the host without root. One open is one request: write the request, read the response; the read waits for the answer, a deadline ends it, and closing the file cancels it. `/dev/paddock/.catalog` describes each device. The only device is `echo`, for tests, and every device is off until `[devices]` in the user configuration turns it on. bwrap, docker and podman show it at `/dev/paddock`; srt at the path in `$PADDOCK_DEVICES`. `paddock doctor` checks FUSE and each backend, and `paddock doctor --escape` checks the round trip, the read-only catalog and that one sandbox cannot use the store of another.
- New: `paddock shims install --scope omarchy-agent` puts only the agents that Omarchy's `omarchy-agent` starts in a sandbox: the key, the console, the agents panel, `omarchy agent prompt`, crash reports and the alias `a`. Commands that you type and scripts do not change, and Omarchy's files stay as they are. paddock writes one marked block, a mise wrapper for `omarchy-agent`, into `~/.config/mise/config.toml`, keeps the rest of the file, and runs `mise reshim`. It refuses when the file has its own `[wrappers.omarchy-agent]`. The wrapper runs the real `omarchy-agent` with a private shim folder first on `PATH` for that start; the shim for `omarchy-launch-tui` puts `paddock wrap --` in front of the agent command. `--inline` takes the same path in the current terminal, so a user install in `~/.local/bin` is covered too. `paddock shims remove` removes both scopes and restores the mise config byte for byte. `paddock shims list` shows the scope.
- New: `paddock wrap -- COMMAND` runs an agent command as it is, in a sandbox: the same arguments (no auto-approval flags added or removed), the same folder, the `env` prefix, the shell form `bash -c '…' "$0"`, an absolute path, and the exit code. In the home folder, the agent works in a scratch project, `~/.local/share/paddock/scratch/<agent>` (mode 0700), which the `paddock:` line, `paddock files` and `paddock du` show and `paddock gc --scratch` removes when it is old. For Claude Code, Codex and Grok Build, the account folder in `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `GROK_HOME` is the login of the sandbox (a new `[state.account]` table in the profile); paddock copies it in and out the same way as the main login, never through a symlink, and keeps Omarchy's account pin. A command without a profile runs without a sandbox, with a desktop notification that names it. `PADDOCK_BYPASS=1` runs without a sandbox.
- `paddock doctor` checks the omarchy-agent scope: the wrapper, the shim folder, the dispatch link of `mise reshim`, mise's wrapper folder on `PATH`, a user wrapper outside paddock's block, whether `omarchy-agent` still starts agents the way paddock expects, and whether the default agent has a profile.
- New built-in profiles for the other agents that `omarchy-agent` starts: amp, commandcode, crush, cursor-agent, devin, dsh, freebuff, hermes, kilo, kimi, kiro-cli, mcode, muse, omp, openclaw, ori, pi and qwen. Each has its login and settings files, the telemetry switches that its vendor documents (with the link), and a one-shot mode where one exists. hermes and pi were tested in a sandbox; the entries of the others come from documentation, and `paddock doctor` lists them. `dsh web` gets its one loopback port (3080) forwarded to the host browser. muse keeps its own sandbox, which cannot start inside paddock, so `paddock wrap` runs it on the host with a notice; paddock never turns muse's sandbox off. OpenClaw's agent runs in its gateway service on the host, so its starts from `omarchy-agent` run as before, with a notice; `paddock openclaw` runs its embedded runtime with a state folder of its own.
- Profiles: `auth` entries that end with `/` copy every credential file in a folder (one file per provider); `[[state.settings]]` writes values into the sandbox copy of a settings file, for example to turn off a self-update; `[network] publish` forwards a loopback port to the host; `[launch] wrap_on_host` names why `paddock wrap` runs a harness on the host. Harnesses without a flag for no approvals (pi, ori, freebuff, mcode, dsh, openclaw) need no `yolo_args`.
- Sessions that `omarchy-agent` starts in a sandbox (through `paddock wrap`) show in the usage statistics of the Omarchy agents panel. Other runs keep their history in the sandbox home, because a sandbox-written transcript that the host loads later (`claude --resume`, `codex resume`) could carry instructions out of the sandbox. For Claude Code, paddock binds only the host folder of the current project in `~/.claude/projects` into the sandbox, read-write; the sandbox sees no other project's history. For Codex and Grok Build, which keep history by date or by session, paddock copies new history files back to the host at exit, through `safefs`, and only files that the host does not have or that the sandbox only appended to. Account folders get their own history; isolated logins keep theirs in the sandbox home. Copying history never writes the panel's usage records. A new `[state.history]` profile table (`project_folders`, `copy_back`, `files`) describes this.
- Harness lookup on `PATH` skips version-manager shims and keeps looking, instead of giving up at the first shim.

- `paddock setup`: a first-run wizard. It shows the missing system packages with the install command for the distribution, and offers the shell commands, the launchers, the Omarchy bar widget, the default backend and app workspace folders. Each step says what it changes and how to undo it. A second run shows the state and changes nothing unless you ask. `--yes` with `--shims`/`--no-shims`, `--launchers`/`--no-launchers`, `--plugin`/`--no-plugin`, `--backend NAME` and `--app NAME=DIR` runs it without questions, for scripts and agents. The wizard runs `sudo` only after a yes on a terminal; with `--yes` it prints the command.
- `paddock update`: updates paddock to the latest GitHub release. It downloads the tarball and its `.sha256` into a private folder, checks the checksum and the version that the new binary prints, then replaces the binary atomically, and runs `omarchy plugin update harnessix.paddock` when the bar widget is installed. HTTPS goes only to GitHub hosts, through the host proxy settings, and no redirect to another host is followed. A binary that a pacman package owns is not overwritten; paddock prints what to run instead. `--check` only reports. The command refuses to run inside a sandbox.
- `paddock doctor` says when a newer release exists (checked at most once a day, at most two seconds of waiting, off with `PADDOCK_NO_UPDATE_CHECK=1`), and when a desktop app was updated on the host after its sandbox started.
- README: a quick start at the top of Install. The bar widget from the Omarchy plugin marketplace does not install the `paddock` command.
- Grok Build (xAI's coding agent, `grok`) is a built-in harness: `paddock grok`. paddock finds it through mise or PATH, starts it with `--always-approve`, shares its login (`~/.grok/auth.json`) and MCP tokens, mounts its skills, agents and rules read-only, and reads its MCP servers from `~/.grok/config.toml` and the project `.grok/config.toml`. Shell commands, launchers, the panel and `paddock doctor` pick it up.
- Privacy defaults: paddock turns off vendor telemetry, usage statistics and crash reports in every sandbox, with the switches that each vendor documents. It sets them only inside the sandbox, as variables or in the sandbox copy of a settings file; the host configuration does not change. This covers Claude Code, Codex, Copilot CLI, Gemini CLI, Grok Build and VS Code, and stops a project `opencode.json` from turning on automatic sharing. `paddock explain` shows each switch with its profile. `[privacy] telemetry = "vendor"` in `~/.config/paddock/config.toml` keeps the vendor defaults; a project `paddock.toml` cannot change it.
- `paddock doctor` and `paddock setup` print, for each installed harness and app, where to turn off the use of your data for training. That is an account setting, which no program can change.
- Profiles have a `[privacy]` table: `env`, `args`, `settings` (values in JSON or TOML files in the sandbox home) and `training`.
- Fix: two `paddock doctor --escape` runs at the same time no longer delete each other's files. Each run now has its own scratch folder (`~/.cache/paddock/doctor-runs/<pid>-<random>`, mode 0700) and its own sandbox home, and removes both when it ends, also after an error. The removal never follows a link that the probe planted. A new run removes what crashed runs left. The folder is new, so a run of an older paddock, which clears `~/.cache/paddock/doctor` at its start, cannot delete it. The homes of ended escape runs are in the automatic tier of `paddock gc`, so `paddock du` no longer collects `doctor` homes.
- Security: the desktop notifications after an app worked in a worktree, and for an app that could not start from a launcher, go to the desktop bus directly instead of through `notify-send`. Before, a branch name, path or error text from a sandbox that started with `-` was read as a `notify-send` option, and every local user could read the text in `/proc`. The Paddock panel's notice for new files outside a project passes only the file count to `notify-send`, after `--`; it no longer names the project.
- New: `paddock-host spawn HARNESS --prompt-file FILE` lets an agent in a sandbox start an agent of another harness, in a second sandbox next to its own, with one task. `paddock-host status`, `wait` and `kill` follow it. The child runs the harness's one-shot mode (`claude -p`, `codex exec`, `opencode run`, `copilot -p`, `agy --print`, `grok --prompt-file`; a new `[oneshot]` table in the profile) in a new worktree on the branch `paddock/spawn-<harness>-<id>`. The parent gets the branch name, a diff summary and the end of the final output in `.paddock/inbox/spawn-<id>/`. Spawn is off until `[spawn] harnesses` in `~/.config/paddock/config.toml` lists a harness; a project `paddock.toml` cannot turn it on. `[host] spawn` is `ask` by default, and `[spawn] max_running` (2), `max_depth` (1: a child cannot spawn) and `timeout` (1800 seconds) set the limits.
- A child never gets more than its parent: the same backend, network mode, LAN setting, environment mode, approved mounts and project, no display, and host capability modes that are at most the parent's. It uses the parent's settings from its start, so a later change to `paddock.toml` does not reach it. It uses its own harness login, and the parent never sees it. The first spawn of each harness asks, and the card shows the harness, the login and the task. A session grant covers only that harness. Requests from a child show "Started by sandbox X", and session grants never pass between parent and child.
- A child stops when its parent ends, when `paddock stop` stops the parent, and after its timeout. `paddock ps` lists children under their parent. `paddock log` records the parent, the child, the harness, the branch, the exit status and the durations, never the task. The task never goes into a process's arguments: the harness reads it on stdin or from a private file. `paddock doctor --escape` checks that a sandbox cannot spawn with a prompt file from outside the project.
- Bar panel: a sandbox that another sandbox started shows under its parent, with the name of the parent. Stopping a parent from the panel says that its children stop too. The approval card names the sandbox that started the asking sandbox.
- Spawn trees in paddock kv. A spawned sandbox reads its parent's `self` scope as `parent`, read-only; paddock takes the parent from the job that the parent's paddock wrote, never from a request. A new `tree` scope is shared by the sandbox that you started and every sandbox below it: all of them read and write it, each entry records its writer, and leases in it let siblings split tasks with compare-and-swap. Only a sandbox above the owner of a lease, or you on the host, can force its release. The scope is on as soon as a sandbox can use spawn. When the root ends, the tree is read-only; `paddock kv list --tree ROOT-ID` shows it until `paddock gc` removes it after `keep_days`. When a child ends, paddock writes `result:<id>` into `tree` with `status`, `summary` and `ref` (the branch), so the parent can watch `result:` instead of polling.
- A spawned sandbox never gets more than its parent in paddock kv and devices: it writes only its own scope and `tree`, not `project` (`[kv] child_project_write = true` allows it); it inherits the parent's session grant for the `user` scope, and without one it is refused and never asks you itself; its `/dev/paddock` has at most the parent's devices. `paddock doctor --escape` checks that a sandbox cannot read the tree scope of another spawn tree.
- Spawn roles, `--from-head` and limits. `--role reviewer` gives the child read-only files and refuses `git push` and `gh` writes; `--role implementer` (the default) gives it its own writable worktree. Every child gets a clean environment. `--from-head` makes a commit of the parent's current files, with uncommitted and new files, through a private index, and the child starts from it; the parent's files, index and branches do not change. `--timeout`, `--mem` and `--cpus` can only lower `[spawn] timeout`, `max_mem` and `max_cpus`. With `systemd-run --user`, the child runs in a systemd scope with `MemoryMax`, `CPUQuota` and `RuntimeMaxSec`; without it, paddock enforces the timeout and refuses memory and CPU limits. The audit log records the role, the limits and why a child stopped.

## 0.1.7

A security release. Update from every earlier version. The docker and podman relay sent the user name and password of an `https://` host proxy in cleartext, and connected directly when it could not use the proxy URL. `recover --to` could be redirected into a protected folder, and a project file could reveal secrets to a flatpak app without approval.

- Security: if the host proxy URL uses a scheme that the docker and podman relay cannot use (for example `socks4://`), the relay refuses connections. Before, it connected directly, which changed the exit address that the user chose.
- Security: `paddock recover --to` walks to the target folder one folder at a time without following symlinks, checks where the opened folder really is, and creates the file in it. Before, it checked the path and then opened it again, so a sandbox that can write a folder on that path could swap it for a symlink in between and make paddock create a new file in a protected place such as `~/.ssh`.
- Security: a flatpak app start asks for approval of a project `paddock.toml` that widens access, the same as every other sandbox. Before, a project `[secrets] reveal` applied without approval and exposed a `.env` to a flatpak app.
- Security: the docker and podman egress proxy talks TLS to an `https://` host proxy. Before, it dropped the `https` scheme and sent the CONNECT request with the `Proxy-Authorization` header in plain TCP, so the proxy user name and password crossed the network in cleartext, even when the proxy then refused the request. Now the request and the credentials go only inside TLS, the proxy certificate must pass a check against the system trust store, and any TLS error fails the request instead of falling back to plain TCP. A remote `http://` or `socks5://` proxy with a user name in its URL still gets it in cleartext, as those protocols do, and paddock logs a warning. Reported in the Omarchy plugin marketplace review.

## 0.1.6

A security release. Update from every earlier version. It fixes four issues: the docker and podman proxy let IPv4-mapped addresses reach loopback and the LAN, a project's MCP config could mount other host folders, private request text was readable by other local users, and flatpak apps did not get the workspace protections. If you used `clipboard-write` with an older paddock, delete `~/.local/state/paddock/host-audit.jsonl`: older lines can hold clipboard text.

- Security: the docker and podman egress proxy treats IPv4-mapped (`::ffff:a.b.c.d`), IPv4-compatible and NAT64 (`64:ff9b::a.b.c.d`) IPv6 addresses as their IPv4 address in its loopback, host and LAN checks. Before, `::ffff:127.0.0.1` passed as "not loopback". The proxy also connects only to the addresses that it checked, so a second DNS lookup cannot point a name somewhere else. Reported in the Omarchy plugin marketplace review.
- Security: a project file was able to give the sandbox read access to other host folders. An MCP server in a project `.mcp.json` (or `opencode.json`, or the project `.gemini/settings.json`) whose command was a file in another repository's `node_modules` counted as a tool install, and paddock mounted that whole repository read-only at the next start, even if the server never ran. The sandbox was then able to read the files of that repository, such as its `.env`. Now a project file gets no implicit trust outside the project, system folders and the shared tool installs in the home, which paddock finds at their real location instead of by a folder name. Any other path, and any interpreter that a script header names, needs `[mcp] allow`, which a project `paddock.toml` sets only with your approval. `paddock mcp` lists the exact host paths that an approval mounts. For a package, paddock now mounts its `node_modules` folder, not the folder around it, and for a file in `~/.cargo/bin`, `~/go/bin`, `~/.bun/bin` or `~/.deno/bin` only that file. paddock hides credential-shaped files in every folder it mounts for an MCP server or for `[mounts]`, as it does in the project. The harness and MCP commands are no longer looked up in relative PATH entries, and paddock refuses a harness whose executable or interpreter is in a folder that the sandbox can write. `paddock doctor --escape` checks that a project `.mcp.json` that names another repository's package mounts nothing of it. Reported in the Omarchy plugin marketplace review.
- Security: other local users were able to read private request text. The host audit log kept up to 500 characters of each clipboard-write request, also for denied and timed-out requests, and a umask of 022 made the log readable by everyone. When the bar did not run, the approval notification passed the same text to `notify-send` as an argument, which every user can read in `/proc`. Now the audit log and the agent approver log keep no request text: only lengths for the clipboard, notifications and `gh` bodies, the program name for `exec`, and the scheme and host for URLs. Notifications go to the desktop bus directly, and `gh` reads the body text with `--body-file -` on its standard input. paddock creates its state, data, cache and runtime folders with mode 0700 and its files with mode 0600, and tightens older ones when it opens them. Lines that an older paddock wrote to `~/.local/state/paddock/host-audit.jsonl` and `approver-decisions.jsonl` can still hold clipboard text: delete those files to remove it. Keyring passwords and copied logins are private from the first byte. Reported in the Omarchy plugin marketplace review.
- Security: flatpak apps (`[app] flatpak = "ID"`) got their workspace folders without the git and secrets protection and without the path policy. The app was able to read a `.env` in a workspace folder, or change `.git/config` or add a hook that git then ran on the host, and a home folder or a folder such as `~/.ssh` was accepted as a workspace folder. It also got the whole host environment, with tokens and the control channels of the host session. Now each folder of a flatpak app goes through the same git and secrets detectors and the same policy as for other apps: `.git` is a mount point of its own, its `config`, `config.worktree`, `commondir`, `gitdir`, `objects/info/alternates` and `hooks` are read-only, `secrets.hide` folders are hidden, and protected paths are refused. flatpak cannot hide a single file, so paddock refuses to start a flatpak app when the secrets detector finds a file such as `.env` in its folders, and names the files. `unprotected_workspaces = true` in `[apps.NAME]` of `~/.config/paddock/config.toml` (never a project file) starts it anyway, with a warning on every start, in `paddock app list` and in the bar panel. `flatpak run` gets the same host environment filter as other sandboxes. Reported in the Omarchy plugin marketplace review.

## 0.1.5

A security release. Update from every earlier version: a sandbox was able to run a command on the host through git, and to make paddock on the host read or write outside the sandbox in more places than 0.1.4 fixed.

- Security: a sandbox was able to run a command on the host through git. The read-only binds of `.git/config` and `.git/hooks` did not hold: inside the sandbox, `mv .git .git2 && mkdir .git` put a fresh, writable `.git` on the host, a new `.git/commondir` sent git's configuration lookup to another directory, and in `--worktree` mode the worktree's `.git` file was writable. Host git calls after a run, such as the worktree report and the session comparison, then read that configuration, and `core.fsmonitor` or a `filter` driver starts a program. `core.worktree` also moved what paddock mounted read-write. Now `.git` is a mount point of its own, so it cannot be renamed, and `config`, `config.worktree`, `commondir`, `gitdir` and `objects/info/alternates` are read-only in it. paddock finds the repository with the file system instead of trusting those files, and refuses a layout that does not match. Every host git call names the git directory, drops the global and system configuration and turns off the settings that start programs; work-tree state comes from a `git status` in a sandbox with no network. `git worktree add` and `git worktree remove` are refused when the repository configuration holds a key that starts a program. The git-push capability checks the object store again right before the push, through the no-follow file layer. `paddock doctor --escape` has new checks for each of these.
- Security: `toml_set` (for example Codex's project trust in `~/.codex/config.toml`) reads and writes the sandbox home through the no-follow file layer too. A symlink left in the home by an earlier run made paddock on the host create or change a file outside the home. Reported in the Omarchy plugin marketplace review.
- Security: more host steps no longer follow what a sandbox leaves in folders it can write. `fetch` opens the path before it asks, shows where it leads, checks it again after your answer, and copies what it opened, so a swap during the wait cannot copy a login into the sandbox. It refuses pipes, devices and folders that hold a protected path, and it also protects harness logins. A docker or podman start makes mount points in the sandbox home without following a symlink there. `mounts.rw`, `mounts.ro`, `secrets.hide` and app workspace folders refuse a path that goes through a symlink in a sandbox-writable folder. The host `mise which` runs in `/` and loads no project config. The login port forwarder and `paddock app open` refuse a symlinked socket. Reads of project files after exit, MCP and mise config, `paddock.toml` and `ports.json` never open a pipe or a device and have a size limit. `paddock init`, the srt temporary folder, the doctor keyring cleanup and `paddock gc` never write or delete through a symlink. `paddock doctor --escape` plants a pipe, a `/dev/zero` link and home links, and checks that the host does not follow them.

## 0.1.4

A security release. Update from every earlier version: a sandbox was able to make paddock on the host read or write files outside the sandbox through symlinks.

- Security: host-side file operations in folders that a sandbox can write no longer follow symlinks. A sandbox was able to replace a file or folder in its home or in the project with a symlink, so that paddock on the host read or wrote somewhere else. The credential sync could copy a host file into the credential store, and the store could then bring it back into the sandbox. The `.gitconfig`, settings and seed copies, and the screenshot and fetch results in `.paddock/inbox`, could write outside the sandbox. Now paddock walks such paths one folder at a time without following symlinks, writes a new file and renames it into place, and never deletes an existing result. Thanks to the Omarchy plugin marketplace review for the report.

## 0.1.3

This release fixes a security problem. Update from earlier versions: in 0.1.2 and before, a project's `mise.toml` was able to replace tools that sandboxes of other projects run. It also adds `paddock du` and `paddock gc`, and smaller docker and podman images.

- Security: a project's mise config was able to change tools that other projects run. The provision step ran `mise install` with the project mounted, and the shared mise installs were writable in that step. A hook, an `[env]` script or a plugin backend in `mise.toml` was able to replace a tool in them, and the agent can edit `mise.toml` for the next start. Now paddock reads the tool list on the host. A clean sandbox without the project installs only registry tools (`core` and `aqua` backends, plain versions) into the shared installs. Other tools install into the private sandbox home. The shared installs are read-only in every project sandbox. They moved to a new folder, `~/.cache/paddock/shared/mise-tools`. You can delete the old folder, `~/.cache/paddock/shared/mise-installs`.
- The docker and podman base images share their layers: one core layer, one desktop layer for every display, app and keyring variant, and the project's own packages. Before, each variant was a separate full image. The first start after the update builds the new image once.
- `paddock gc` counts only the part of an image that removing it frees, and also removes paddock's own records in the docker build cache, which held the data of removed images. Before, it added up full image sizes, so it reported space that it did not free.
- srt backend: a host tool in a system folder, such as mise in `/usr/bin`, no longer comes first on PATH. Before, `gh` in a project with a mise file ran the host `gh` instead of paddock's `gh`, which goes through the host.
- `paddock doctor --escape` gives its test project a `mise.toml` whose `[env]` script and hooks try to write into the shared installs, and checks that they cannot. With `--online`, it checks that a registry tool from `mise.toml` installs into the shared installs.
- `paddock du` shows the disk space of each sandbox home, with its harness, login, project, last use and what deleting it loses. It also lists the paddock images of docker and podman, the worktrees with their unmerged commits, the session records and the keyring passwords. On btrfs, sizes are exclusive bytes. `--json` prints JSON.
- `paddock gc` removes paddock data that is no longer needed. It is a dry run unless you add `--yes`. `--yes` removes old paddock images that no container uses, keyring passwords without a home, session records that ended more than 30 days ago, homes of harnesses without a profile, and the old `mise-installs` cache. paddock does the same after it builds a new image (`PADDOCK_GC_AFTER_BUILD=0` turns that off). `--homes` adds homes whose project is gone or that were not used for `--older-than` days, and desktop app homes also need `--include-app-logins`. `--worktrees` adds worktrees, and those with unmerged commits also need `--force`. gc never touches a running sandbox, deletes only inside paddock's own directories and never follows a symlink.
- Each sandbox home has a `.paddock-origin` file with its project, harness, login, last use and whether it is a desktop app. `du` and `gc` use it only when it matches the folder name of the home. Homes from before this release show "unknown" and their last change.

## 0.1.1

Highlights: push and open pull requests from a sandbox without credentials, an encrypted keyring for desktop apps, a worktree for each app, files saved outside the project that you can recover, and the LAN blocked by default.

- A menu start of an app without saved workspace folders asks for one in a dialog: a recent project or any folder. Before, the start failed without a message.
- `paddock doctor` lists the commands that shims take over, the rc file that loads them, the one-off bypass and how to turn them off. `paddock shims list` marks each command on or off.
- Releases include a prebuilt `x86_64` Linux binary and its SHA-256 checksum.
- App mode: each app gets a private session bus inside the sandbox, with a private keyring. Claude, ChatGPT and VS Code store their logins and secrets encrypted there, and Claude no longer warns that no system keyring is available. `paddock portal` on that bus sends the app's web links to the host browser after your approval, and its notifications to your desktop. The app gets no file chooser portal and cannot reach the host bus. `[apps.NAME] bus = "host-filtered"` keeps the filtered host bus. `paddock doctor --escape --app` checks the private bus, and `--bus host-filtered` checks the other one.
- App mode: a login page that an app opens through paddock and that returns to a localhost port reaches the app without `login_ports`, the same way as for terminal harnesses.
- Push and open pull requests from a sandbox without credentials in it. Plain `git push` goes to the new `git-push` host capability: the host pushes with your credentials after you see the remote, the branches, the commits and the force flag. Force pushes, pushes to the default branch and pushes to a remote that the sandbox names itself ask every time. Hooks never run on the host.
- The `forge` host capability runs a fixed set of `gh` commands (pull requests, issues, CI runs) on the project's own repository with your login. Reads run without a question and writes ask. Plain `gh` in the sandbox uses it.
- Inherit mode drops forge tokens such as `GH_TOKEN`, `GITHUB_TOKEN` and `GITLAB_TOKEN`, unless `[env] pass` or a profile names them.
- `paddock doctor --escape` checks that the sandbox has no git credentials, that `git push` becomes a `git-push` request, that a remote named in the sandbox is flagged, that a force push cannot get a session grant, and that a denied push exits with code 3.
- App worktrees: `paddock app run NAME --worktree`, or `[apps.NAME] worktree = true`, opens the first workspace folder in a new git worktree on the branch `paddock/<app>-<date>-<id>`. The folder dialog of a menu start offers it as the default for git repositories. When the app exits, paddock lists the worktree's commits and uncommitted changes.
- A sandbox started from a Claude app session no longer inherits the app's control channel (`CLAUDE_CODE_MESSAGING_TOKEN` and `CLAUDE_CODE_MESSAGING_SOCKET`).
- Network mode `egress` blocks the LAN by default: private, link-local and CGNAT ranges, on every backend. `[network] lan = true` allows it again. `paddock doctor --escape` checks it.
- Logging with levels. `-v` and `-q` change how much paddock prints, and `PADDOCK_LOG=debug` or `PADDOCK_LOG=broker=debug` sets the level for everything or for one part. The broker, the proxy, the login callback forwarder and the window border also write to the systemd journal: `journalctl -t paddock -p warning`.
- `paddock doctor --report` prints a diagnostic report for bug reports, without user names, paths, variable values or tokens.
- The bar plugin writes a warning to the shell log when it cannot read paddock's output. `PADDOCK_DEBUG=true` shows more.
- Sandbox artifacts: `paddock files` lists the files that a sandbox saved outside the project, in recovery folders such as `~/Desktop` and `~/Downloads`, and the project changes since the start. `paddock recover` copies them to the host without overwriting anything, and `paddock discard` deletes them. The Omarchy panel lists them and sends a notice when new ones appear. Set the folders in `[recovery]` of `~/.config/paddock/config.toml`.
- `paddock shims install` makes the sandbox the default: typing `claude`, `codex` and the other harness commands in bash or zsh starts them in a sandbox. `paddock shims remove` undoes it, and nothing breaks if paddock is removed first.
- A `paddock` agent skill for the host, next to `paddock-host`. Install both with `npx skills add harnessix/omarchy-paddock`.

## 0.1.0

The first public release.

- `paddock <harness>` runs a coding-agent harness with full auto-approval in a sandbox. The sandbox sees the project, a private home and nothing else of your files.
- Backends: bwrap (the default), docker, podman and srt.
- Network: outbound only. The bwrap backend uses pasta and blocks the addresses of the host. Containers reach the internet through a relay proxy only. Your system proxy and VPN routes stay as they are.
- Logins: isolated logins per harness, login callbacks through an approval, and a private keyring for harnesses that need one.
- Host requests: a sandbox can ask to open a link or use a host capability. You answer once, for the session, or deny, from an approval card or from `paddock approvals`.
- App mode: `paddock app run` runs a desktop app, such as VS Code, in a sandbox, with a marked window border.
- Displays for desktop projects: a private headless or window display, and `paddock-screenshot`.
- Launchers: `paddock launchers install` adds menu entries for the harnesses and apps that paddock finds.
- Omarchy bar plugin: lists sandboxes, starts new ones, shows recent requests and runs `paddock doctor`.
- `paddock doctor` and `paddock doctor --escape` test the setup and the sandbox limits.
